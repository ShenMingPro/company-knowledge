# 混合检索实现总结

## 一、实现目标

为 RAG 系统添加轻量级混合检索功能，结合向量检索和 BM25 关键词检索的优势，通过 RRF（Reciprocal Rank Fusion）算法融合两路结果，提升检索召回率和准确性。

**核心原则**：
- 简单、稳定、容易解释
- 不引入新的模型 API
- 保持现有权限、版本、生命周期规则
- 适合大模型应用开发实习简历展示

## 二、为什么需要混合检索

### 向量检索的局限性
- **语义理解强，但对精确匹配弱**：向量检索擅长理解语义相似性，但对产品型号（如 KB-R2）、故障码（如 E03）、版本号（如 V5.2）等精确匹配不敏感
- **数字和符号处理差**：电压参数（220V）、错误代码（HTTP-500）等容易被忽略
- **同义词干扰**：语义相近但实际不同的内容可能被误召回

### BM25 关键词检索的优势
- **精确匹配能力强**：能准确匹配产品型号、故障码、参数值
- **词频统计稳定**：基于 TF-IDF 原理，对高频关键词有良好的判别能力
- **计算开销小**：不需要调用模型，速度快

### 混合检索的价值
- **互补性**：向量检索提供语义理解，BM25 提供精确匹配
- **鲁棒性**：一路失败时可以降级使用另一路
- **召回率提升**：两路检索覆盖更广，不容易遗漏相关文档

## 三、技术方案

### 3.1 整体架构

```
用户查询
    ↓
权限和版本过滤（获取 accessible_space_ids 和 valid_version_ids）
    ↓
┌─────────────────────────────────────────┐
│          混合检索器 (HybridRetriever)          │
├─────────────────────────────────────────┤
│  ┌───────────────┐    ┌──────────────┐  │
│  │  向量检索 (10) │    │ BM25 检索 (10)│  │
│  │  Chroma       │    │  rank-bm25   │  │
│  └───────┬───────┘    └──────┬───────┘  │
│          │                   │          │
│          └────────┬──────────┘          │
│                   ↓                      │
│          ┌────────────────┐             │
│          │  RRF 融合算法   │             │
│          │  去重 + 排序    │             │
│          └────────┬───────┘             │
│                   ↓                      │
│             Top 6 候选                   │
└─────────────────────────────────────────┘
    ↓
可信 RAG 生成答案（现有流程）
    ↓
返回结果（带引用、耗时、检索模式统计）
```

### 3.2 中文分词策略

**分词工具**：jieba（中文分词库）
- 使用搜索模式（`cut_for_search`）：细粒度分词，提高召回率
- 例如："扫地机器人" → ["扫地", "机器", "机器人", "扫地机器人"]

**文本规范化**：
1. 英文统一转小写
2. 保留产品型号、故障码、版本号（KB-R2、E03、220V 等）
3. 过滤单字符（除数字和字母）
4. 不使用复杂停用词表

**查询和文档一致性**：
- 查询文本和文档文本使用完全相同的分词和规范化逻辑
- 确保关键词能够正确匹配

### 3.3 BM25 检索实现

**核心类**：`rag/bm25_retriever.py` - `BM25Retriever`

**索引构建**：
- **时机**：查询时动态构建（内存索引）
- **语料来源**：从 Chroma 读取已通过权限和版本过滤的分片
- **必要条件**：
  - `space_id` 在 `accessible_space_ids` 中
  - `document_version_id` 在 `valid_version_ids` 中
  - `is_active` 为 `True`
  - 存在 `document_id`、`document_version_id`、`chunk_index`

**检索流程**：
1. 对查询进行分词和规范化
2. 使用 `rank-bm25` 库计算 BM25 分数
3. 按分数降序排序
4. 返回 Top K 结果（分数 > 0）

**返回格式**：
```python
{
    'document': Document,
    'bm25_score': float,  # BM25 原始分数
    'bm25_rank': int      # 排名（1, 2, 3...）
}
```

### 3.4 RRF 融合算法

**公式**：
```
rrf_score(doc) = 1 / (rrf_constant + vector_rank) + 1 / (rrf_constant + bm25_rank)
```

**参数**：
- `rrf_constant`：默认 60（业界常用值）
- `vector_candidate_k`：向量检索候选数（默认 10）
- `bm25_candidate_k`：BM25 检索候选数（默认 10）
- `final_top_k`：最终返回数量（默认 6）

**融合规则**：
1. 向量和 BM25 各自先排序
2. 使用 `document_version_id + chunk_index` 作为唯一标识去重
3. 同一分片同时出现在两路时，累加 RRF 分数
4. 只出现在一路的候选保留该路 RRF 分数
5. 按 RRF 分数降序排序
6. 分数相同时，依次比较 `vector_rank`、`bm25_rank`、`chunk_key`

**为什么使用 RRF 而不是直接相加原始分数**：
- 向量距离和 BM25 分数量纲不同（距离 vs 词频统计）
- 直接相加会导致某一路占主导地位
- RRF 基于排名融合，消除了量纲差异
- RRF 对排名靠前的文档给予更高权重

### 3.5 BM25-only 候选处理

**场景**：某些文档只被 BM25 召回，未被向量检索召回

**处理规则**：
1. BM25-only 候选可以进入最终结果
2. 必须满足：
   - BM25 分数 > 0
   - 至少命中一个有效查询词
   - 通过权限和版本过滤
3. 字段设置：
   - `vector_distance = None`
   - `vector_rank = None`
   - `relevance_score = None`
   - `bm25_score = 实际分数`
   - `bm25_rank = 实际排名`
4. **不伪造向量相关度**：`relevance_score` 保持 `None`，不将 BM25 分数转换为向量相关度

**相关性阈值过滤**：
- 向量相关性阈值（1.2）只适用于有 `vector_distance` 的候选
- BM25-only 候选跳过相关性阈值过滤（因为没有向量距离）

## 四、权限和版本过滤

### 4.1 过滤顺序

```
1. 获取用户角色 (user_role)
2. 获取可访问知识空间 (accessible_space_ids)
   ↓ 如果为空，直接拒绝
3. 获取当前有效版本 (valid_version_ids)
   ↓ 如果为空，返回空结果
4. 向量检索（带过滤条件）
5. BM25 检索（使用相同过滤条件）
6. RRF 融合
7. 返回 Top K
```

### 4.2 BM25 语料过滤

**不允许**：
- 让无权限或旧版本文档进入 BM25 语料
- 跨空间或跨版本检索

**语料获取**：
```python
filter_dict = {
    "$and": [
        {"space_id": {"$in": accessible_space_ids}},
        {"document_version_id": {"$in": valid_version_ids}},
        {"is_active": {"$eq": True}}
    ]
}
corpus = chroma.get(where=filter_dict, limit=10000)
```

**额外检查**：
- 过滤掉缺少 `document_id`、`document_version_id`、`chunk_index` 的旧数据

### 4.3 空角色和未知角色

- 空角色（`user_role=None`）：直接返回空结果，不进入检索
- 未知角色（权限查询返回空）：同样返回空结果
- 无可访问知识空间：向量和 BM25 都不执行

## 五、失败降级策略

### 5.1 降级规则

| 场景 | 处理方式 |
|------|---------|
| BM25 失败 + 向量成功 | 使用向量结果，记录 warning |
| 向量失败 + BM25 成功 | 使用 BM25 结果（必须符合权限和版本规则） |
| 两个通道都失败 | 返回空结果，拒答 |
| 权限查询失败 | 拒绝检索，不允许降级为全库检索 |

### 5.2 降级不能绕过规则

任何降级都**不能绕过**：
- 权限过滤
- 版本过滤
- 文档删除规则

## 六、配置管理

**配置文件**：`config/chroma.yml`

```yaml
hybrid_retrieval:
  enabled: true               # 是否启用混合检索
  vector_candidate_k: 10      # 向量检索候选数
  bm25_candidate_k: 10        # BM25 检索候选数
  final_top_k: 6              # 最终返回数量
  rrf_constant: 60            # RRF 常数
```

**运行时控制**：
```python
# 使用混合检索（默认）
rag = RagSummarizeService(user_role='employee')

# 禁用混合检索，使用纯向量
rag = RagSummarizeService(user_role='employee', use_hybrid=False)
```

## 十、当前限制

### 10.1 已知限制

1. **查询时构建 BM25 索引**
   - 每次查询都重新构建内存 BM25 索引
   - 文档数量较多时（> 1000 个分片）可能影响性能
   - 优点：实现简单，数据一致性好，文档更新、下架和版本切换后无旧索引问题

2. **未实现增量索引**
   - 文档更新后需要重新构建整个索引
   - 未持久化 BM25 索引到磁盘

### 10.2 不影响使用的限制

- **中文停用词**：未使用停用词表，但对结果影响较小
- **语料规模**：当前实现限制为 10000 个分片，对小型知识库足够
- **分词细节**：jieba 对部分专业术语可能分词不准确，但整体可用

### 10.3 未来可优化方向

1. **持久化 BM25 索引**：将 BM25 索引持久化到磁盘，避免每次查询重建
2. **增量更新**：文档更新时只更新相关部分的索引
3. **分词优化**：维护领域词典和停用词表，改善专业术语召回
4. **效果实验**：基于真实业务数据持续对比召回、精排和回答质量

## 十一、总结

### 11.1 实现成果

✅ 实现了向量检索 + BM25 关键词检索 + RRF 融合的轻量混合检索方案
✅ 保持了现有权限、版本、生命周期、审计和反馈规则
✅ 支持中文分词，保留产品型号、故障码、参数等关键信息
✅ 实现了 BM25-only 候选处理，不伪造向量相关度
✅ 实现了失败降级策略，提升鲁棒性
✅ 20 个新测试全部通过，14 个现有测试不回归
✅ 配置化管理，可灵活启用/禁用混合检索

### 11.2 技术特点

- **简单**：使用查询时构建的内存 BM25 索引，实现简单，无需复杂的增量更新逻辑
- **稳定**：权限和版本过滤在检索前完成，降级不绕过规则
- **容易解释**：RRF 融合算法易于理解，检索模式和通道可追溯

### 11.3 适用场景

本实现适合：
- 知识库规模较小（< 1000 文档）
- 对实时性要求不高（可接受查询时构建索引的延迟）
- 需要精确匹配产品型号、故障码、参数等信息
- 需要简单、稳定、容易维护的解决方案
- 用于大模型应用开发实习简历展示

### 11.4 声明

**本模块实现本地 BM25 关键词检索与向量检索的轻量混合方案，通过 RRF 融合两路排名；当前系统已在其后接入 Query 改写、Reranker 和离线评测，但效果结论仍应以具体数据集的评测结果为准。**
